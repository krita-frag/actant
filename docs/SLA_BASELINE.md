# Actant SLA 行为基线（单机）

> **定位声明**：本文档记录的是**单机**（单节点 + 本地 worker 进程池）混沌/压力场景下
> 观测到的行为基线。**多机（≥3 节点 P2P）数据待补**；单机数字受本机负载与硬件差异影响，
> 仅作为后续回归对比的参考点，不构成对外承诺。
>
> 契约以 `tests/python/e2e/test_chaos_baseline.py`
> 与 `tests/python/e2e/test_multi_node_reliability.py` 中的可执行断言为准（§3.5 取消场景的
> 断言位于 `tests/python/unit/test_task.py::TestCancellation`）——本文档的观测值
> 是这些断言运行时打印的 sideline 数据，**不设 CI 阈值门禁**（CI 机器噪声大，待基线稳定后
> 由维护者决定是否加回归阈值）。

## 1. 环境与配置

| 项 | 值 |
|----|-----|
| 平台 | macOS 14.7.8（Darwin 23.6.0），arm64（Apple Silicon） |
| Python | CPython 3.11.14 |
| CPU | 10 核 |
| 执行后端 | 进程池（worker 子进程，`python -m actant.task._worker`），线程后端已移除 |
| 版本 | 0.3.5 工作树（含 0.3.4 身份与信任 / Actor 精简 / F3 与 0.3.5 前五批；manifest 版本号仍为 0.3.0，与里程碑标签解耦） |
| 发现模式 | `ACTANT_DISCOVERY=none`（测试离线约定，无 DNS/relay 干扰） |

## 2. 方法学

- **场景即测试**：每个场景是 `test_chaos_baseline.py` 中一个独立用例，断言只覆盖 SLA 契约
  （正确性、零丢失、最终收敛），吞吐/内存/恢复时间以 `print("[chaos-baseline] ...")` 输出，
  人工抄录进本文档（`pytest -s` 可复现）。
- **计时**：`time.monotonic()` 包裹「提交 → `gather` 全部收敛」整段；吞吐 = 任务数 / 该段时长，
  含序列化、IPC、调度与结果回传全链路开销。
- **内存**：父进程峰值 RSS，`resource.getrusage(RUSAGE_SELF).ru_maxrss`（macOS 单位字节）。
- **每次用例总时长 ≤ 60s**；轮询断言 + 总超时，无固定 sleep。
- 同场景重复运行 2 次以上取区间；样本量小，仅用于量级对比。
- **机器状态**：观测须在**空闲机器**上采集——并发的构建/测试会显著拉长收敛时长。
  0.3.3 复跑在空闲机器上进行（此前 0.3.1 基线采集时的负载状态未记录）。
- **计时分辨率**：elapsed 以秒为单位打印两位小数，亚 0.05s 场景（大 fan-out）
  已接近分辨率上限，由 elapsed 导出的 ops 相对误差可达 ±30% 以上，不得当作
  吞吐波动的证据。

## 3. 场景契约与观测值

### 3.1 打满队列（背压零丢失）

- **SLA 契约**：提交量远超 `max_concurrent_tasks` 的任务全部最终完成——超额提交只增加延迟
  （信号量背压排队），不产生丢失、失败或结果错位。
- **配置**：`max_concurrent_tasks=2`，提交 100 个 noop 任务（50x 超额），`gather(timeout=55s)`。
- **断言**：100/100 返回且值全部正确。
- **观测**：

| 批次 | 运行 | 收敛时长 | 吞吐 |
|------|------|---------|------|
| 0.3.1 基线 | 1–2 | 0.08s | ~1296 / ~1228 ops/s |
| 0.3.3 复跑 | 1–4 | 0.04s（4 次一致） | ~2452 / ~2310 / ~2512 / ~2246 ops/s |
| 0.3.5 复跑 | 1–2 | 0.04s（2 次一致） | ~2454 / ~2410 ops/s |

### 3.2 大 fan-out / fan-in

- **SLA 契约**：单节点一次性提交 200 个任务，全部正确聚合（fan-out/fan-in 无丢失）。
- **配置**：默认并发度（`max_concurrent_tasks = CPU 核数 = 10`），200 个 noop 任务，
  `gather(timeout=55s)`。
- **断言**：200/200 返回且值全部正确。吞吐与内存为 sideline 观测值，不参与断言。
- **观测**：

| 批次 | 运行 | 收敛时长 | 吞吐 | 父进程峰值 RSS | 本次增量 |
|------|------|---------|------|---------------|---------|
| 0.3.1 基线 | 1–2 | 0.18s / 0.17s | ~1102 / ~1180 ops/s | 84.4 / 88.5 MiB | +1.1 / +1.2 MiB |
| 0.3.3 复跑 | 1–4 | 0.02s（4 次一致） | ~12153 / ~10816 / ~11545 / ~8610 ops/s | 93.5 / 93.0 / 95.7 / 92.7 MiB | +1.2 / +1.4 / +2.3 / +1.6 MiB |
| 0.3.5 复跑 | 1–2 | 0.06 / 0.07s | ~3139 / ~2935 ops/s | 89.9 / 90.6 MiB | +2.9 / +3.2 MiB |

> ⚠️ **不可跨版本直接对比**：0.3.3 复跑的 0.02s 已贴近计时分辨率，导出的 ops
> 相对误差很大（故区间宽达 8.6k–12.2k，**不代表吞吐真实波动**）；而 0.3.1 基线的
> 0.17–0.18s 可能包含了更冷的进程池状态。两组数字只能各自作为**同版本回归参考点**。
> 后续刷新建议把 n 提高到数千，使 elapsed 远离分辨率。
> 内存口径可比：峰值 RSS 从 ~84–88 MiB 升至 ~93–96 MiB，fan-out 边际增量
> 仍在 MiB 量级（+1.2 ~ +2.3 MiB），未见量级变化。

（每次用例独立 Runtime，RSS 峰值为进程生命周期累计值；「本次增量」为该用例前后的差，
即 200 任务 fan-out 的边际内存占用在 MiB 量级。）

### 3.3 慢消费者

- **SLA 契约**：慢任务占满 worker 后，后续任务排队不丢；慢任务结束后排队批次全部收敛。
- **配置**：`max_concurrent_tasks=2`；先提交 2 个 1.5s 慢任务占满 worker，再提交 20 个
  快速任务排队。
- **断言**：慢任务与排队任务的 22/22 结果全部正确。
- **观测**：0.3.1 基线（2 次）总收敛时长均 1.55s；0.3.5 复跑（2 次）均 1.54s；
  0.3.3 复跑（4 次）
  1.55 / 1.56 / 1.56 / 1.55s——**与基线一致**。排队 20 个任务的边际等待 ≈ 0.05s，
  即排队成本主要为等待慢任务释放槽位（1 个排队批次深度 ≈ 慢任务时长），调度本身无显著开销。

### 3.4 worker 崩溃恢复（引用 H1 可靠性矩阵 + 探针观测）

- **SLA 契约**：
  1. worker 子进程崩溃属基础设施级失败，任务清空 `target_node` 重新入队重路由
     （上限 `crash_failover_max_attempts=3`，超限降级为终态失败）；
  2. 崩溃只影响单任务，节点存活，后续任务正常；
  3. 崩溃与硬超时不占用业务重试（`retries`）配额。
- **观测**（`crash_once` 探针：首次执行 SIGKILL 自杀 worker，重路由第二次执行成功）：
  - 崩溃 → 重路由 → 成功：**0.55s**（本机、热池）；
  - 恢复后节点吞吐：50 个快速任务 0.02s 收敛（~2400 ops/s），节点无降级。
  - 持续崩溃任务在有界尝试内到达终态失败，批次内其他任务不受影响
    （可执行断言见 `test_multi_node_reliability.py::TestWorkerKillIsolation`）。
- **0.3.3 复跑**：H1 可靠性矩阵（`tests/python/e2e/test_multi_node_reliability.py`）
  在本机以 `--basetemp` 绕开 `tmp_path` 沙箱限制后**真实执行**——
  `TestNodeKill` / `TestNodeRestartResume` / `TestWorkerKillIsolation` /
  `TestOutOfOrderResults` 全部通过。其中
  `test_node_kill_inflight_task_terminal_state` 仍为 **xfail**（见 §4 已知边界）。

### 3.5 取消结算与传播（0.3.3 S6/S7 收尾）

- **SLA 契约**：
  1. **取消必须结算 DAG**——工作流内节点被取消后，工作流本身必须进入终态
     （`Cancelled`），不得停留在 `Running`（否则 flow 提交方轮询永不返回）；
  2. **终态类别优先级**：全部节点终态时 `Failed > Cancelled > Completed`，
     无结果不得当成功；
  3. **取消不得被归类为失败**——已取消的任务不得进入业务重试队列（"取消被
     复活"），也不得把工作流误判为 `Failed`；
  4. **取消不得静默丢失**——任务尚在调度器队列（未开始执行）时提交的取消
     请求必须被登记，并在派发时被采纳；
  5. 工作流以取消收尾时计入 `actant.workflows.cancelled` 指标，并发独立的
     `WorkflowEventPayload::Cancelled` 终态事件（不复用 `Failed`）。
- **配置**：`@flow` 体内提交 2 个长任务，`a.cancel(propagate=True,
  force_after=0.5)` 取消整个工作流。
- **可执行断言**：
  `tests/python/unit/test_task.py::TestCancellation::test_propagate_cancels_same_workflow_tasks`
  （契约的唯一执行载体）；失败行为回归见 `tests/rust/unit/runtime/workflow/`
  的 5 个新增用例（全取消 fail-fast 终态、部分取消不误报 Completed、
  seal 前取消不终态、取消派发结果映射、派发前取消登记）。
- **观测**（本机 macOS arm64，连跑 5 次）：**0.52–1.59s** 全部返回，工作流终态
  `Cancelled`。**修复前**同一用例连跑 3 次：2 次挂起至 60s 超时、1 次耗时
  **10.74s**（两个任务各跑满 10s——取消实际未生效，靠任务自然结束兜底）。
  量级差异（~10.7s / 挂起 → ~0.5s）是本批次最显著的基线变化。

## 4. 已知边界

- **执行密度上限：1 进程 = 1 任务**：本地并发上限恒等于 worker 进程数（默认 CPU 核数），
  与任务是否 I/O 密集无关——I/O 等待期间整个 worker 进程闲置。后果：I/O 密集 fan-out 的
  墙钟时间 ≥ ⌈任务数 / 进程数⌉ × 单任务 I/O 时长（例：200 个 1s I/O 任务在 10 进程上
  ≥ 20s，无论 CPU 多空闲）。这是"硬超时精确杀单任务"身份的直接代价（杀进程即杀任务，
  一进程多任务会把强杀扩大化）。缓解：加大 `num_worker_processes`、批量 gather 提交、
  等待 0.3.2 Ref 减少载荷搬运。放宽此上限的"密集 worker 模式"仅在出现真实
  I/O 密集用户时再裁决。
- **分区语义（诚实声明）**：网络分区下故障转移依赖租约 + gossip 最终一致；旧主与新主存在
  有限的双执行窗口（结果接受侧 attempt fencing 丢弃过期代际的结果，但副作用可能已发生）——
  与所有无中心系统一样，任务函数需要幂等。完整信任边界文档随 0.3.4（身份与信任）落地。
- **在途直提任务无重认领路径（xfail 记录）**：执行节点被强杀后，**存活编排器**上
  已派往该节点的**直提任务**（`submit_to`，非工作流节点）无重认领路径——failover 的
  claim 重调度只覆盖"死亡编排器的孤儿 workflow"。该任务的 `AsyncResult` 保持挂起，
  30s 内不达终态。可执行记录：
  `test_multi_node_reliability.py::TestNodeKill::test_node_kill_inflight_task_terminal_state`
  （`xfail(strict=False)`）。同源缺口：`actant/flow.py` 的 `_replay_flow`（S3 续跑入口，
  按既有 `workflow_id` 重放 flow 体）**全仓零调用方**、不在 `__all__`——即"节点重启
  自动续跑"尚无公开接线，重启只能恢复状态、不能自动重放未完成的 flow 体。
- **单机基线**：所有数字来自单节点 + 本地进程池；多节点 P2P（跨机网络、gossip 收敛、
  远端 failover）的吞吐/恢复时间数据待补，预计受网络 RTT 主导，不可由本文档外推。
- **Windows 未验证**：本基线在 macOS arm64 观测；worker IPC 已统一为 stdio pipe
  （SHM ring 已移除，Windows/POSIX 行为归一），行为等价性由 CI 冒烟用例保障，性能数字未测。
- **量级参考而非承诺**：样本 2 次运行、单机、离线发现模式；数字随硬件/负载漂移，
  CI 不做阈值断言（deliberate choice，理由见 bench workflow 的注释）。
- **冷/热池差异**：首次提交含 worker 子进程冷启动（每进程 ~百 ms 量级）；表中吞吐均为
  同用例内批量提交的摊销值，与单任务冷启动延迟（AGENTS.md 记载 ~6ms IPC 往返物理下限）
  属不同口径，不可混用。
