# Actant SLA 行为基线（单机）

> **定位声明**：本文档记录的是**单机**（单节点 + 本地 worker 进程池）混沌/压力场景下
> 观测到的行为基线。**多机（≥3 节点 P2P）数据待补**；单机数字受本机负载与硬件差异影响，
> 仅作为后续回归对比的参考点，不构成对外承诺。
>
> 对应 0.3.1 硬化项 H2（plans/PLAN.md §2.2）。契约以 `tests/python/e2e/test_chaos_baseline.py`
> 与 `tests/python/e2e/test_multi_node_reliability.py` 中的可执行断言为准——本文档的观测值
> 是这些断言运行时打印的 sideline 数据，**不设 CI 阈值门禁**（CI 机器噪声大，待基线稳定后
> 由维护者决定是否加回归阈值）。

## 1. 环境与配置

| 项 | 值 |
|----|-----|
| 平台 | macOS 14.7.8（Darwin 23.6.0），arm64（Apple Silicon） |
| Python | CPython 3.11.14 |
| CPU | 10 核 |
| 执行后端 | 进程池（worker 子进程，`python -m actant.task._worker`），线程后端已移除 |
| 版本 | 0.3.0 + 0.3.1 硬化批次（未发布工作树） |
| 发现模式 | `ACTANT_DISCOVERY=none`（测试离线约定，无 DNS/relay 干扰） |

## 2. 方法学

- **场景即测试**：每个场景是 `test_chaos_baseline.py` 中一个独立用例，断言只覆盖 SLA 契约
  （正确性、零丢失、最终收敛），吞吐/内存/恢复时间以 `print("[chaos-baseline] ...")` 输出，
  人工抄录进本文档（`pytest -s` 可复现）。
- **计时**：`time.monotonic()` 包裹「提交 → `gather` 全部收敛」整段；吞吐 = 任务数 / 该段时长，
  含序列化、IPC、调度与结果回传全链路开销。
- **内存**：父进程峰值 RSS，`resource.getrusage(RUSAGE_SELF).ru_maxrss`（macOS 单位字节）。
- **每次用例总时长 ≤ 60s**；轮询断言 + 总超时，无固定 sleep。
- 同场景重复运行 2 次以上取区间；样本量小，仅用于量级对比。

## 3. 场景契约与观测值

### 3.1 打满队列（背压零丢失）

- **SLA 契约**：提交量远超 `max_concurrent_tasks` 的任务全部最终完成——超额提交只增加延迟
  （信号量背压排队），不产生丢失、失败或结果错位。
- **配置**：`max_concurrent_tasks=2`，提交 100 个 noop 任务（50x 超额），`gather(timeout=55s)`。
- **断言**：100/100 返回且值全部正确。
- **观测**（2 次运行）：

| 运行 | 收敛时长 | 吞吐 |
|------|---------|------|
| 1 | 0.08s | ~1296 ops/s |
| 2 | 0.08s | ~1228 ops/s |

### 3.2 大 fan-out / fan-in

- **SLA 契约**：单节点一次性提交 200 个任务，全部正确聚合（fan-out/fan-in 无丢失）。
- **配置**：默认并发度（`max_concurrent_tasks = CPU 核数 = 10`），200 个 noop 任务，
  `gather(timeout=55s)`。
- **断言**：200/200 返回且值全部正确。吞吐与内存为 sideline 观测值，不参与断言。
- **观测**（2 次运行）：

| 运行 | 收敛时长 | 吞吐 | 父进程峰值 RSS | 本次增量 |
|------|---------|------|---------------|---------|
| 1 | 0.18s | ~1102 ops/s | 84.4 MiB | +1.1 MiB |
| 2 | 0.17s | ~1180 ops/s | 88.5 MiB | +1.2 MiB |

（每次用例独立 Runtime，RSS 峰值为进程生命周期累计值；「本次增量」为该用例前后的差，
即 200 任务 fan-out 的边际内存占用在 MiB 量级。）

### 3.3 慢消费者

- **SLA 契约**：慢任务占满 worker 后，后续任务排队不丢；慢任务结束后排队批次全部收敛。
- **配置**：`max_concurrent_tasks=2`；先提交 2 个 1.5s 慢任务占满 worker，再提交 20 个
  快速任务排队。
- **断言**：慢任务与排队任务的 22/22 结果全部正确。
- **观测**（2 次运行）：总收敛时长均 1.55s——排队 20 个任务的边际等待 ≈ 0.05s，
  即排队成本主要为等待慢任务释放槽位（1 个排队批次深度 ≈ 慢任务时长），调度本身无显著开销。

### 3.4 worker 崩溃恢复（引用 H1 可靠性矩阵 + 探针观测）

- **SLA 契约**：
  1. worker 子进程崩溃属基础设施级失败，任务清空 `target_node` 重新入队重路由
     （上限 `crash_failover_max_attempts=3`，超限降级为终态失败）；
  2. 崩溃只影响单任务，节点存活，后续任务正常；
  3. 崩溃与硬超时不占用业务重试（`retries`）配额。
- **观测**（`crash_once` 探针：首次执行 SIGKILL 自杀 worker，重路由第二次执行成功）：
  - 崩溃 → 重路由 → 成功：**0.55s**（本机、热池）；
  - 恢复后节点吞吐：50 个快速任务 0.02s 收敛（~2400 ops/s），节点无降级。
  - 持续崩溃任务在有界尝试内到达终态失败，批次内其他任务不受影响
    （可执行断言见 `test_multi_node_reliability.py::TestWorkerKillIsolation`）。

## 4. 已知边界

- **执行密度上限：1 进程 = 1 任务**：本地并发上限恒等于 worker 进程数（默认 CPU 核数），
  与任务是否 I/O 密集无关——I/O 等待期间整个 worker 进程闲置。后果：I/O 密集 fan-out 的
  墙钟时间 ≥ ⌈任务数 / 进程数⌉ × 单任务 I/O 时长（例：200 个 1s I/O 任务在 10 进程上
  ≥ 20s，无论 CPU 多空闲）。这是"硬超时精确杀单任务"身份的直接代价（杀进程即杀任务，
  一进程多任务会把强杀扩大化）。缓解：加大 `num_worker_processes`、批量 gather 提交、
  等待 0.3.2 Ref 减少载荷搬运。放宽此上限的"密集 worker 模式"已登记为设计裁决 J1
  （`plans/ROADMAP.md` §设计裁决登记），仅在出现真实 I/O 密集用户时裁决。
- **分区语义（诚实声明）**：网络分区下故障转移依赖租约 + gossip 最终一致；旧主与新主存在
  有限的双执行窗口（结果接受侧 attempt fencing 丢弃过期代际的结果，但副作用可能已发生）——
  与所有无中心系统一样，任务函数需要幂等。完整信任边界文档随 0.3.4（身份与信任）落地。
- **单机基线**：所有数字来自单节点 + 本地进程池；多节点 P2P（跨机网络、gossip 收敛、
  远端 failover）的吞吐/恢复时间数据待补，预计受网络 RTT 主导，不可由本文档外推。
- **Windows 未验证**：本基线在 macOS arm64 观测；worker IPC 已统一为 stdio pipe
  （SHM ring 已移除，Windows/POSIX 行为归一），行为等价性由 CI 冒烟用例保障，性能数字未测。
- **量级参考而非承诺**：样本 2 次运行、单机、离线发现模式；数字随硬件/负载漂移，
  CI 不做阈值断言（deliberate choice，见 `plans/PLAN.md` H8 与 bench workflow 注释）。
- **冷/热池差异**：首次提交含 worker 子进程冷启动（每进程 ~百 ms 量级）；表中吞吐均为
  同用例内批量提交的摊销值，与单任务冷启动延迟（AGENTS.md 记载 ~6ms IPC 往返物理下限）
  属不同口径，不可混用。
